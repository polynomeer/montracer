# ADR 0070: 설정 > Access 화면 — API key 발급·목록·폐기 (F07 — 화면)

- 상태: 승인 (결정 위임 — polynomeer, 2026-10-05 "빅테크 사례 기준으로 결정하고 근거를 기록". 2026-10-21 다음 작업 선택 "API key 관리 API·화면")
- Owner: Frontend lead
- 날짜: 2026-10-21 (제안·결정)
- 관련: F07, E01 · D05 §01(Admin), §03(상태 계약), §04 · D05 §10 S13("key는 생성 시 한 번만 보여주고 복사 성공과 노출 주의를 제공한다") · ADR 0068(Team 화면, step-up 안내), 0069(key API)

## 배경

ADR 0069로 key API가 생겼다. D05 Admin 탐색 영역의 Access(`settings/access`)는 아직 placeholder다. 정할 것은 네 가지다.

- 발급 양식이 무엇을 기본으로 고르는가
- 원문 1회 표시
- 교체 겹침을 고르는 방법
- 상태 표시

## 결정

### 1. 위치와 권한 표시

- 화면은 `/o/{org}/settings/access`다. 조회는 Tenant Admin만이다. 다른 역할이 열면 서버 403에 따라 "볼 권한이 없습니다"를 보인다.
- 발급·폐기는 step-up이 필요하다. 안내는 Team 화면(ADR 0068 §2)과 같은 구성 요소를 쓴다. 문구만 "key 발급·폐기"로 바꾼다.

### 2. 발급 양식

- **종류를 먼저 고른다.** 수집(OTLP)이 기본이다. 수집기 연결이 가장 흔한 첫 작업이다(D05 S13 설치 흐름의 key 단계).
  - 종류를 바꾸면 scope와 기간이 그 종류의 기본값으로 바뀐다.
  - 수집: trace·metric·log 모두, 365일.
  - API: telemetry 조회만, 90일. 최소 권한에서 시작한다.
- **scope**는 사람이 읽는 설명과 action 이름을 함께 보인다. 서버가 다시 검사한다.
  - API key 설명에 "내 현재 권한을 넘지 못합니다"를 둔다(ADR 0015 §1).
- **environment**는 쉼표·공백으로 여럿을 받는다. 수집은 필수, API는 비우면 "조직 전체"다.
- **기간**은 30·90·180·365일 중에서 고른다. 만료 없는 선택지는 없다(ADR 0069).
- 화면 검증은 서버와 같은 규칙이다: scope 1개 이상, environment 형식·20개, 이름 64자·제어 문자 없음.
  - 오류는 그 입력 아래에 두고 `aria-describedby`로 묶는다. 보내기를 누르면 첫 오류 입력으로 focus를 옮긴다(D05 §03).
  - 서버 거절(400)은 서버 문장을 보인다.
- 실패하면 쓴 값을 남긴다.
- **같은 양식의 다시 보내기는 같은 Idempotency-Key다.** 응답을 잃고(연결 오류·5xx) 다시 눌러도 key가 둘 생기지 않는다(D02 §20).
  - 성공하거나 입력이 바뀌면 새 key다.
  - 재생 응답에는 원문이 없으므로 "폐기하고 새로 발급하세요"를 보인다.

### 3. 원문 1회 표시

- 알림 policy secret·초대 링크와 같은 방식이다(ADR 0056·0068).
  - 상태에만 두고, 닫으면 사라진다.
  - 제목에 focus를 주고 role=alert는 쓰지 않는다.
  - 복사 버튼과 실패 안내가 있다.
- D05 S13 "복사 성공과 노출 주의"에 따라 두 가지를 덧붙인다.
  - "저장한 뒤 클립보드를 비우세요"
  - 쓰는 방법(`Authorization: Bearer <key>`)
- 재생 응답(원문 없음)이면 "폐기하고 새로 발급하세요"를 보인다.

### 4. 목록과 상태

- 열은 이름(없으면 "이름 없음"), `token_hint`, 발급자·시각, 종류·scope, environment, 상태, 만료다.
- **상태는 서버 시각을 지금과 비교만 한다.** 끝나는 시각은 만료와 폐기 중 이른 쪽이다.
  - **유효**: "사용 중"이라 하지 않는다. 마지막 사용 시각은 아직 없다(ADR 0069). 화면에 그 사실과 교체 때 확인할 지표를 적는다.
  - "HH:MM에 폐기"(교체 중 — 폐기가 만료보다 먼저이고 미래)
  - 폐기됨
  - 만료됨
  - **확인할 수 없음**: 시각을 읽지 못함. 정상으로 치지 않는다(계약 6).
- 열어 둔 동안 다음 만료·폐기 시각이 되면 다시 그린다.
- 새로고침이 실패해 마지막 목록을 보일 때는 "유효(마지막 확인 기준)"로 낮춰 보인다. stale 결과에 정상 배지를 붙이지 않는다(D05 §03).
- 목록이 상한(1,000개)에 닿으면 "1,000개 이상·최근만 보임"을 알린다.
- 폐기·만료된 key도 목록에 남긴다. 언제 끝났는지 확인할 수 있다(ADR 0069).

### 5. 폐기와 교체

- 행 안에서 확인한다(빼기와 같은 방식, ADR 0068). 시점은 "지금 / 1시간 뒤 / 24시간 뒤(교체 중)" 중에서 고른다.
  - 교체 절차(새 key 발급 → 배포 → 이전 key를 겹쳐 폐기, D04 §02)를 한 화면에서 끝낸다.
- 확인에는 영향을 적는다: "이 key를 쓰는 수집기·SDK(또는 자동화·CI)는 {시각}부터 401로 거절됩니다".
- 확인이 열리면 시점 선택으로 focus가 가고, 취소하면 "폐기…" 버튼으로 돌아온다. 원문 표시를 닫으면 양식 제목으로 간다.
- 성공 문장은 고른 값을 단정하지 않는다. 이미 더 이른 폐기가 있으면 서버가 그대로 두기 때문이다(멱등). 실제 시각은 목록 상태로 본다.

## 후보

| 후보 | 이점 | 비용·위험 |
|---|---|---|
| A (채택) 종류 먼저·종류별 기본값(수집 전체 365일, API 조회 90일)·폐기 시점 선택 | 첫 수집기 연결이 짧다. API key는 최소 권한에서 시작한다 | 1년마다 수집 key 교체가 필요하다(만료 알림은 ADR 0069 재검토 조건) |
| B 기본 scope 없음(전부 직접 고르기) | 의도가 분명하다 | 흔한 수집 key 발급에 클릭이 늘어난다 |
| C 교체 전용 "교체" 버튼(새 key 발급 + 이전 key 예약 폐기) | 한 번에 끝난다 | 새 key의 scope를 바꾸기 어렵다. API에 없는 동작이다(ADR 0069 후보 C) |

## 결과

- 이점: 고객이 수집기·CI key를 화면에서 발급·교체·폐기한다.
- 영향 받는 계약
  - web route `/o/{org}/settings/access`
  - dev proxy가 `/api/v1/keys…`를 control-api로 보낸다
  - consumer contract가 fixture를 OpenAPI로 검사한다

## Rollback

이전 web 빌드로 되돌린다. API는 ADR 0069 flag로 따로 끈다.

## 재검토 조건

- 만료 전 알림(ADR 0069)이 생기면 목록에 "곧 만료" 표시를 더한다.
- S13 설치 흐름이 생기면 그 흐름 안에서 수집 key를 발급하게 하고, 이 화면과 같은 구성 요소를 쓴다.

## 근거 (빅테크 사례)

- **GitHub fine-grained PAT 화면**: 이름·만료(선택지와 직접 지정)·권한 선택 뒤 만들기. token은 한 번만 보이고 "다시 볼 수 없습니다"를 알린다. 목록은 만료·마지막 사용을 보인다.
- **AWS IAM access key 화면**: 활성·비활성 상태를 보이고, 교체는 새 key 만들기와 이전 key 비활성화로 한다. secret은 만들 때 한 번만 내려받는다.
- **Grafana service account token**: 이름·만료 선택, 한 번만 보이는 token과 복사 버튼.

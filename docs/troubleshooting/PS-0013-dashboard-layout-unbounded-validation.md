# PS-0013: dashboard 검증이 배치 수에 상한 없이 겹침을 O(n²)로 세어 큰 본문 하나로 메모리를 쓸 수 있었음

- 날짜: 2026-10-14 (발견) / 2026-10-14 (해결)
- 영역: control-api — `internal/dashboard` DashboardSpec 검증
- 영향: 가용성 — Developer key 하나로 control-api 메모리를 크게 쓸 수 있었다(재현하지 않은 계산상 위험). 출시 전(같은 PR 리뷰)에 고쳤다. 데이터·tenant 영향 없음. 심각도 P1(리뷰)
- 수정: ADR 0057 PR(같은 브랜치), `internal/dashboard/spec.go` `Normalize`
- 관련: ADR 0057 §1, D02 §14 "최대 50 위젯", D02 §15 실행 예산

## 증상

spec-reviewer가 첫 구현에서 다음 경로를 찾았다.
- `layout[]` 길이에 상한이 없었다. 위젯 50개 상한·변수 10개 상한은 오류만 기록하고 검증을 끝까지 계속했다.
- 배치 겹침 검사는 모든 쌍(O(n²))을 보며, 겹칠 때마다 오류를 하나씩 쌓았다. 위젯을 가리키지 않는 배치도 겹침 검사에 들어갔다.
- 본문 상한 256KiB 안에 `{"x":0,"y":0,"w":1,"h":1}` 배치를 약 1만 개 넣으면 서로 모두 겹친다. 그러면 오류 약 5천만 개를 `fmt.Sprintf`로 만들고, 오류 응답도 그만큼 커진다.

## 발견 경위

PR 전 spec-reviewer 검토(P1). 단위 시험은 정상 크기의 거절만 봐서 놓쳤다.

## 원인

"모든 오류를 한 번에 돌려준다"는 검증 방식(monitor와 같다)을 개수 상한에도 그대로 썼다. 개수 상한을 넘은 입력은 항목별 검증 비용이 입력 크기에 따라 커진다(겹침은 제곱). 본문 byte 상한만으로는 항목 수가 묶이지 않았다.

## 해결

- 개수 상한(변수 10, 위젯 50, 배치 50)을 항목 검증보다 먼저 보고, 넘으면 오류 하나로 바로 거절한다. 그래서 겹침 검사는 최대 50×49/2쌍이다.
- 겹침은 위젯을 가리키는 유효한 배치끼리만 본다.
- 버린 대안: 오류 수 상한(예: 100개에서 멈춤)만 두기. 겹침 계산 자체(제곱)가 남고, 개수 상한이 먼저 걸리면 필요 없다.

## 재발 방지

- 시험: `internal/dashboard/spec_test.go` `TestOversizedCollectionsRejectFast`
  - 배치 5,000개는 오류 하나(`layout`)로 바로 거절된다.
  - 서로 겹치는 50개는 오류가 50×49/2 이하다.
  - 변수 11개는 오류 하나다.
- 검토 기준: 새 검증기는 "항목 수 상한을 먼저, 항목 검증은 그 뒤"로 쓴다.

## 교훈

본문 크기 상한은 항목 수 상한이 아니다. 쌍·중첩을 세는 검증(겹침, 중복, 참조)은 항목 수를 먼저 묶은 뒤에 돌린다.
